# Does a guided cascade beat a fixed tier at the same budget?

**No.** On thirty hard documents, no version of the cascade produced more whole
documents than simply choosing a better fixed routing — and the better fixed
routing costs half as much.

Measured 21 August 2026 from stored rows. No GPU.

## The rule, which has no parameters

> For each field, run the routed tier. If the returned value is absent from the
> document or fails its declared shape rule, run the tier above and keep the
> second answer.

No threshold to tune, because both signals are binary. A threshold fitted on this
corpus would use the very data that bounds its interval; a rule without one
escapes the objection instead of working around it.

## Seven columns

30 documents with all five fields. Ladder by price:
`rules < gen-0.6b < small < gen-4b < gen-8b < large`.

| | whole docs | escalations | €/1000 | ms/doc |
|---|---|---|---|---|
| 1. current fixed routing | 0/30 | 0 | 1.84 | 968 |
| 2. guided cascade, as specified | 0/30 | 6 | 1.91 | 1,239 |
| 2b. guided, blanks included | 0/30 | 90 | 2.12 | 1,889 |
| 2c. escalate to `gen-8b`, blanks included | **1/30** | 103 | 3.10 | 4,960 |
| 3. random cascade, same spend as 2b | 0/30 | 90 | 2.19 | 2,202 |
| 4. oracle, one step | 0/30 | 40 | 1.97 | 1,424 |
| **5. best fixed routing at 2b's budget** | **2/30** | 0 | **0.99** | 3,273 |

## What the numbers say, and what they cannot

**The recommended routing completes nothing on broken documents.** It sends three
of five fields to `rules`, which returns a blank 133 times in 164 on this corpus.
Zero whole documents, and no cascade repairs that, because the failure is not a
wrong value to catch — it is an empty one.

**The rule as specified almost never fires.** Six times in a hundred and fifty.
Both signals inspect a returned value, and `rules` mostly returns nothing. That
was the rule's blind spot, not a property of the corpus, and it is the first
thing the measurement showed.

**Including blanks makes it fire ninety times and still returns nothing.** The
tier one step above `rules` is `gen-0.6b`, which is not good enough to complete a
document either.

**Even the oracle returns 0/30.** Perfect foresight, escalating one step, changes
nothing. One step is not the limitation of the *signal*; it is the limitation of
the *ladder*.

**Escalating to the top tier finds one document — for 68 % more money and five
times the latency.** One document in thirty.

**And the column that wins was not a cascade at all.** The best fixed routing
inside the cascade's budget completes two documents at 0.99 € per thousand,
nearly half the cascade's 2.12, though three times slower. Every euro the cascade
spent on second calls would have bought more by being spent on a better first
call.

## The reservation that governs everything above

**Zero, one and two out of thirty.** This repository does not publish a rate below
twenty successes, and these counts are far under it. Nothing here is
statistically distinguishable from anything else here.

So the honest reading is not "the cascade loses by one document". It is: **on this
corpus, at these counts, no version of the cascade shows a gain, and the only
column that produced whole documents did so by changing the fixed routing rather
than by cascading.** A larger hard corpus could overturn every line of the table.

What the measurement does establish, because it does not depend on the counts:
the recommended routing collapses on broken documents, its dominant failure mode
is the blank rather than the wrong value, and a cascade built on signals that only
inspect returned values cannot see that failure at all.

## Where the price ladder comes from, since it drives the escalation order

`large` is the most expensive tier here, above `gen-8b`. That is not an error:
`large` is priced as a hosted API at 1.60 per thousand extractions, while the
generative tiers are priced by local machine time — `gen-8b` at 1,101 ms costs
about 0.37 per thousand at 1.20 per machine-hour. Change `pricePerThousandLarge`
in the assumptions and the ladder, and therefore the escalation order, changes
with it.

## Two sources, kept apart

Correctness comes from the hard-corpus rows. Price and latency come from the
published relevé's latencies, measured on an idle machine. The hard corpus's own
durations describe different documents and are not used here.
